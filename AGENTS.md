# AGENTS.md

Monoio (published as `adaptif-gatotkaca-monoio`, library name `monoio`): a stripped-down, thread-per-core async runtime built only on io_uring. Linux only, kernel 5.6+. There is no epoll/legacy/IOCP driver. A fork of bytedance/monoio; keep `LICENSE-*` and `NOTICE` when changing licensing or packaging.

## Layout
- `monoio/`: the runtime crate (package `adaptif-gatotkaca-monoio`; refer to it as `-p adaptif-gatotkaca-monoio`).
  - `src/`: `builder`, `runtime`, `scheduler`, `task`, `driver/uring` (+ `op`), `io` (rent traits), `buf`, `net/{tcp,udp,unix}`, `fs`, `time`, `blocking`, `macros` (`join!`, `select!`, `try_join!`), `utils`, `tls/{rustls,native}` (feature-gated; `tls/io_wrapper.rs` bridges the sync TLS engines to rent IO).
  - `tests/`: integration tests; most need a working io_uring.
  - `examples/`: load reproducers that pin a server runtime to one CPU and clients to others (`--cpu`, `--client-cpus`), built with `cargo build --release -p adaptif-gatotkaca-monoio --example <name>`: `fairness` (bulk streams, open-loop request/response, accept ramp), `smallframes` (many connections, small frames, a `timeout` per frame), `thread_per_core` (echo server on `ThreadPerCore`), `reqresp` (closed-loop request/response: `--conns N` connections send `--sizes 4k,16k,64k` frames and wait for a 70-byte reply, `--bulk M` bulk writers next to them; `--path plain|pipe|mshot|eager` is the server loop, `--ring coop,defer,skipenter,ringfd,fixedfd,minwait<us>,drain<N>` the ring, `--deadline none|timeout|coarse|deadline` the per-frame deadline, `--wset I,S` the working set of the `mshot` ring, `--direct` direct accept; prints frames/s, reply p50/p99, user instructions per frame, and with `metrics` both stats structs).
- `monoio-macros/`: separate proc-macro crate (package `adaptif-gatotkaca-monoio-macros`; proc macros cannot live in the runtime crate, so it is published first): proc macros `#[monoio::main]`, `#[monoio::test]`, `#[monoio::test_all]`, and `select!` internals.
- `examples/`: unpublished crate, built with default features off. Run one with `cargo run -p monoio-examples --example echo`. Examples: accept, builder, channel, echo, echo-tfo, join, macro, proxy, tcp_uring, timer, timer-select, uds, tls-{rustls,native}-{server,client} (certs in `monoio/tests/certs`).

## Commands
- Check: `cargo check --workspace`
- Test: `cargo test -p adaptif-gatotkaca-monoio` (add `--features splice,mkdirat,...` for the optional ops; they need a new enough kernel)
- Format and lint: `cargo fmt`, `cargo clippy --workspace` (style is in `rustfmt.toml`; some options are nightly-only)
- Stable Rust 1.85+ (the `adaptif-gatotkaca-utils` dependency uses edition 2024). Only the `unstable` feature needs nightly.

## Core concepts
- **Thread-per-core.** Each thread owns one `Runtime`. Tasks are `!Send`; thread-local state is fine. `monoio::spawn` runs on the current thread only. Use it for IO-bound servers, not for unbalanced CPU work.
- **Ownership-based IO ("async rent").** Calls take the buffer by value and return it: `let (res, buf) = stream.read(buf).await;`. The kernel may touch the buffer after the future is dropped, so borrowed buffers are unsound. Buffers implement `IoBuf`/`IoBufMut` (`IoVecBuf`/`IoVecBufMut` for vectored IO). Do not expect Tokio's `AsyncRead`/`AsyncWrite`; there is no compat layer.
- **Traits.** `AsyncReadRent`, `AsyncWriteRent` and their `*Ext` traits (`read_exact`, `write_all`, ...). They use async-fn-in-trait / `impl Future` returns, not GAT or `poll_*`.
- **Cancellation.** Dropping a future cannot reliably stop an in-flight op (and with `async-cancel` only tries to). For timeouts use the `Cancelable*` traits:
  ```rust
  let canceler = monoio::io::Canceller::new();
  let fut = conn.cancelable_read(buf, canceler.handle());
  // on timeout: canceler.cancel(); then keep awaiting `fut`
  ```
  Always await the future after `cancel()`: you get the buffer back, and the result is either `Err(os error 125)` (ECANCELED) or a completed result you must handle. Wrappers just pass the `CancelHandle` through.
- **Yielding.** `monoio::task::yield_now().await` puts the task at the back of the ready queue. With `coop_budget`, `task::consume_budget().await` spends one unit in CPU loops, and `task::unconstrained(fut)` runs `fut` without a budget.
- **Communication.** Same thread: `local-sync` (mpsc, oneshot, semaphore, no atomics). Between runtime threads, no `sync` needed: `uring::msg_ring` (see below). From any thread (runtime or not) into a runtime thread: `uring::event_channel()`, a lock-free channel carrying any `T: Send`:
  - `EventSender` (`Send + Sync + Clone`): `send(v) -> Result<(), SendError<T>>` never blocks; `SendError::Full(v)` when the channel is at capacity, `Disconnected(v)` when the receiver is gone (`into_inner()` gives `v` back).
  - `EventReceiver` (`!Send`): `recv().await -> Option<T>` (`None` once all senders dropped and the queue is empty; cancel safe), `try_recv()` (doesn't arm a wakeup, so senders pay nothing for it), `stats()` (`capacity`; `eventfd_wakeups`, `ring_wakeups`, `full` and `wakeups()` need the `metrics` feature).
  - Capacity: `uring::EventChannelBuilder::new().initial_capacity(n).max_capacity(m).build()`. Defaults 1024 slots, growing by doubling mmap'd segments up to 131,072 (one in-flight message per connection at 100k connections, with headroom); max 2^31. Pages are faulted in on first use and kept until the channel is gone.
  - How it works: messages go into arena nodes (tagged-index free list) pushed onto a Treiber stack (`adaptif-gatotkaca-utils`); the receiver takes a whole batch with one swap. A sender wakes the receiver only if it is waiting: with `MSG_RING` from a ring thread (directly on the receiver's own ring), with an eventfd write from other threads, so a burst costs one wakeup. In tests it moves about 2× the messages of a mutex queue with 4–8 producer threads.
  - With `sync`, any channel (`flume`, `async-channel`, Tokio's `sync`) or atomics work too. Prefer per-thread aggregation on hot paths.
- **Raw io_uring access.** The `io_uring` crate is re-exported as `monoio::io_uring` (and `opcode`, `squeue`, `cqueue`, `types`, `IoUring`, `Probe` as `monoio::uring::*`): use these instead of depending on `io_uring` yourself, so versions always match. `monoio::uring` is the escape hatch for ops the crate doesn't wrap. `unsafe uring::submit(sqe, data)` queues any `squeue::Entry` and resolves to `(Cqe, data)`; `data` must own the heap memory the SQE points to and is kept alive until the kernel finishes. `unsafe uring::with_ring(|ring| ..)` exposes the `IoUring` for registration, probing and `params()`. Both also exist on `IoUringDriver` (`submit_raw`, `with_ring`; reach it with `Runtime::driver()`). `submit` is for single-shot SQEs; an fd it returns is yours to close. For multishot SQEs use `unsafe uring::submit_multishot(sqe, data)` (or `IoUringDriver::submit_multishot_raw`), see below.
  - **Your own SQEs.** For ops `submit_multishot` can't express (or to route many ops through one table), push them yourself inside `with_ring` with `user_data(uring::user_data(id))` (`id <= uring::MAX_ID`) and receive every completion in a hook: `uring::set_cqe_hook(|id, cqe| ..)` (`Cqe::more()` says a multishot is still armed, `buffer_id()` gives the provided buffer). The driver delivers the hook's batch after it finished its own tick, so the hook may call `with_ring`/`submit`, wake or spawn. Completions are dropped while no hook is installed, so set it first. You own everything those SQEs point to until their last CQE. Never reap the CQ, and never use a `user_data` below 2^62 (it collides with the driver's ops). With the timer enabled, reach the driver with `runtime.driver().inner()`.
- **Registered (fixed) buffers (5.13+).** `uring::FixedBufPool::new(count, size)` (or `new_in(&driver, ..)`) registers `count` buffers of `size` bytes; `pool.get()` returns an owned `FixedBuf` (`IoBuf + IoBufMut`, `Deref<[u8]>`, `buf_index()`), or `None` when empty; it returns to the pool on drop. Use it with `File::read_fixed_at` / `write_fixed_at` and `TcpStream::recv_fixed` / `send_fixed` (each with an `_op` named-future variant), or with any ordinary op. `send_fixed` is `WRITE_FIXED` (the kernel rejects fixed buffers on plain `SEND`), so it has no `MSG_NOSIGNAL`. `buf.freeze()` gives a refcounted, cloneable `FrozenFixedBuf` (`slice(range)` copies nothing); the buffer returns when the last clone drops. `pool.grow(n)` adds buffers without touching those in use; `pool.stats()` gives `in_use`, `capacity` (and `high_water`, `exhausted` with the `metrics` feature). All pools on a ring share one sparse table (`DEFAULT_TABLE_SLOTS` = 1024, larger via `with_table_size`, max 16384) with disjoint index ranges; it is unregistered once the last pool and buffer are gone. While a pool exists, don't call `register_buffers`/`unregister_buffers` raw (a pool after raw registration fails with `EBUSY`). Registration pins the pages, which counts against `ulimit -l` (`ENOMEM`).
- **Provided buffers (`IOSQE_BUFFER_SELECT`, Linux 5.19+).** `uring::BufRing::new(bgid, entries, buf_size)` (or `BufRing::new_in(&driver, ..)`; `entries` a power of two) registers a pool the kernel picks from. Set `squeue::Flags::BUFFER_SELECT` and `.buf_group(ring.group())` on a `Recv` (null ptr, len 0) or use `RecvMulti`, submit via `uring::submit` or the hook, then `ring.take(cqe)` gives a `SelectedBuf`. It is `Deref<[u8]>` and `IoBuf` (write or send it, or a `.slice(..)`, with no copy) and returns to the pool on drop; `detach()`/`into_bytes()` copy it out and return it at once. Call `take` for every completion of the group or the pool runs dry (`ENOBUFS`, counted in `ring.stats()` with `high_water`/`taken`/`recycled`/`grown`/`retired` when the `metrics` feature is on; `in_use` and `published` always). The pool is lazily faulted, page-aligned `mmap` memory. **Size buffers to hold a whole frame**: a frame split over several buffers costs a completion per piece (G1, 64 KiB frames at 8 connections: 72 KiB buffers tie per-connection buffers, 16 KiB buffers lose 6%). Options via `BufRing::with_options(.., uring::BufRingOptions::new()...)`:
  - `batch_publish`: recycled buffers are published once per driver tick (before each `io_uring_enter`, and where `skip_empty_enter` skips one), or earlier by `ring.publish()`.
  - `working_set(initial, step)`: the ring is a FIFO, so with more buffers than are in use at once every receive lands in the buffer idle longest (cache-cold). This publishes only `initial` buffers and keeps the rest in a reserve (a stack, so the published buffers are always the ones used last). It grows by `step` when a `take` leaves no published buffer free and when `wait_free`/`next_rearm` find none, and on `ENOBUFS` by as many as it takes to have `step` free again (at least one); it shrinks, not below `initial`, when over the last `4 × published` takes fewer than half the published buffers were in use at once (down to twice that peak). Size `entries` for the worst case, `initial` for the usual one. `recv_multi`/`recv_multi_bundle` take at reap time on such a ring (as on an incremental one), which is what makes the demand visible; with raw SQEs take in the hook (taking later under-reports the demand, the ring shrinks too far and only `ENOBUFS` grows it back). By hand, on any ring: `ring.published()`, `grow_published(n)` (publishes the buffers retired last), `shrink_published(n)` (takes effect as buffers are recycled; the automatic part continues from the count they set). G1: `working_set(16, 16)` with 72 KiB buffers, all connections on `recv_multi`, ties per-connection buffers at 8 connections (1024-buffer ring) and gains 2% at 2000; at 2000 connections a 4096 × 16 KiB ring settles at about 80 published buffers after the ramp.
  - `kernel_ring`: the kernel allocates the ring (`IOU_PBUF_RING_MMAP`, 6.4+).
  - `incremental`: `IOU_PBUF_RING_INC` (6.12+). Several receives share one buffer; each `SelectedBuf` is a view at `offset()`. The buffer is recycled when the kernel clears `BUF_MORE` and all its views are dropped. `take` must see every completion once, in CQ order: `recv_multi`/`recv_multi_bundle` take at reap time, so many connections can share one ring; raw SQEs: take in the hook (raw `MultiOp`s and single-shot recvs take in poll order, so don't share the ring with other ops). A buffer returns only when all its pieces are consumed, so one slow connection pins a whole buffer: size a shared ring to about `2 × connections × bytes in flight per connection` (more buffers rather than bigger), or recvs end with `ENOBUFS`.
  - `hugetlb` (needs reserved huge pages; errors instead of falling back), `populate`.

  `ring.wait_free().await` (a `WaitFree`, `Unpin`, not tied to the handle) resolves when a buffer is free by the ring's own count (published minus taken, so take completions as they arrive; a working set that can still grow grows instead of waiting). Each buffer that comes back wakes one waiter, the oldest: start a receive when it resolves, or the others keep waiting. Finish or cancel ops using the group before dropping the last `BufRing` and `SelectedBuf`.
- **Socket flags and vectored sends.** `TcpListener`/`UnixListener::accept_with(AcceptFlags::NONBLOCK | AcceptFlags::CLOEXEC)` (and `cancelable_accept_with`) set `accept4` flags; plain `accept()` sets none (monoio never needs `O_NONBLOCK`). `TcpStream`/`UnixStream` (and their owned halves) have `send_with_flags(buf, MsgFlags)`, `recv_with_flags(buf, MsgFlags)` (`monoio::net::MsgFlags::{MORE, WAITALL, DONTWAIT, PEEK, ..}`; sends always add `MSG_NOSIGNAL`), `recv_poll_first(buf, flags)` (`IORING_RECVSEND_POLL_FIRST`, 5.19+, for probably idle connections), and `send_vectored(bufs)` / `send_vectored_with_flags` (`sendmsg` with `MSG_NOSIGNAL`: a reset peer gives EPIPE/ECONNRESET, never SIGPIPE; `writev` still uses `IORING_OP_WRITEV`). `monoio::buf::IoVecArray<B, N>` (write) / `IoVecArrayMut<B, N>` (read) hold up to N buffers and one reused boxed iovec array: keep one per connection, `push`, send, then `drain()`/`clear()`; after a short write call `advance(n)` and send again.
- **Eager sends (direct syscalls).** `TcpStream`/`UnixStream` (and the owned halves) have `try_send(&[u8])`, `try_send_vectored(&[IoSlice])` and `try_recv(&mut [u8])`: one non-blocking `send`/`sendmsg`/`recv` on the calling thread (`MSG_DONTWAIT`; sends add `MSG_NOSIGNAL`), no op slot, no SQE, no CQE. They return `WouldBlock` when the socket is full/empty, when a ring op of that direction is still in flight on the socket (a direct call must not overtake it: the stream counts its ring sends and receives, split halves, `recv_multi`, `read_at_then_send`, `*_with_deadline`, splice and zero-copy sends included; the count can be late, never early), or when the stream is direct-only (no fd). `send_eager(buf)` / `send_eager_with_flags(buf, flags)` return the usual `SendFuture`: ready at its first poll when the direct send took everything (or failed), else a ring `SEND` of the rest with `IORING_RECVSEND_POLL_FIRST` (a plain `send_op` when a send is in flight or the stream is direct-only); the result counts from the start of the buffer, and a ring failure after a partial direct send is reported as that short count. Both the syscall and the SQE push happen in the call, not at the first poll. `set_eager_send(true)` / `eager_send()` (per socket, seen by both halves; off by default) make `write`/`write_all` go through `send_eager` and `writev` try one direct `sendmsg` first; the `_op` methods, `send_with_flags`, `send_vectored`, zero-copy and `cancelable_*` are unchanged. Rules: SQEs you build yourself (`uring::submit`, chains, the hook) are not counted, so don't mix them with these calls on one socket; the direct call is wasted on writes that usually fill the socket buffer (bulk streams): use it for replies up to a few KiB; a zero-copy send counts until the kernel released its buffer, a `RecvStream` until it is dropped; two ring sends in flight on a full socket are not ordered by the kernel, so await a send before starting the next. Meant for `defer_taskrun` rings (or rings without task-run flags): on `coop_taskrun` every syscall also runs the ring's pending task work on its way out, unbatched. G1 (`reqresp --path eager` shape: `send_eager(&REPLY[..])`, then `recv_poll_first_op` for the next frame, in one task poll): at 8 connections the ack p99 falls from 135 to 109 µs, inside tokio's range (103–120), at −1.1% frames/s; at 2000 connections −1.2%.
- **Request/response loops.** Three patterns measured in round 3 (G0/G1): (1) queue the reply and the next receive in the same task poll (`send_op` + `recv_poll_first_op`, or `send_eager` + `recv_poll_first_op`); awaiting the send first costs a whole loop round per request, which next to bulk tasks was the largest loss against tokio in ROUND3.md's first table. (2) Receive buffers must not shrink: `BytesMut::advance` after each request leaves less capacity for the next one, and a request that no longer fits costs a second receive, i.e. a loop round; `clear()` when the buffer is fully consumed (`reqresp` keeps one `Vec` of the largest frame plus slack per connection). (3) `coop_taskrun` or `defer_taskrun`: many connections → `defer` (G1, 2000 connections: `coop` is 13–18% slower, because one enter runs all pending task work and the loop falls into one round per sweep of all connections); few connections next to bulk work used to need `coop`, now `defer` with `drain_taskrun(2)` matches it (see "Recommended configuration for request/response servers" under Runtime configuration).
- **Multishot ops.** `unsafe uring::submit_multishot(sqe, data) -> MultiOp<T>`: the driver queues each CQE of the op (unbounded; see `DriverStats::multishot_queue_high_water`, `metrics` feature). `op.next().await` returns them in order; the CQE without `F_MORE` is the last, then `None`. `op.cancel()` pushes AsyncCancel; keep polling to drain (the end is usually `-ECANCELED`). `into_data()` works once the kernel posted the final CQE. Dropping a `MultiOp` cancels the op (even without `async-cancel`) and keeps `data` alive until the final CQE; dropped raw CQEs are not inspected (fds and provided buffers in them leak), so cancel and drain if that matters. Typed:
  - `TcpListener::accept_multi(AcceptFlags)` / `UnixListener::accept_multi` (5.19+) give an `AcceptStream`: `next()` yields `(stream, addr)` with one `getpeername` syscall each, `next_stream()` skips it; `next_batch(&mut vec, max)` / `next_stream_batch` take everything already queued in one poll. It re-arms itself when the kernel ends the multishot without an error (full CQ); an error ends it. Dropping it closes queued connections.
  - **Server accept loops:** a loop around `accept()` accepts one connection per scheduler round (round 2 G0: ~100/s with 4096 busy connections, accept queue 3,338, ~6,200 timeouts per run; multishot: none). On a `coop_taskrun` ring with many connections one enter runs all pending task work, so the loop makes one round per sweep of all connections (round 3 G0, 2000 connections: 49 rounds/s), and anything that does one operation per round, a single-accept loop above all, is throttled to that rate (ack p99 7.1 s, 22 ms with multishot accept). Use `listener.accept_batch_into(&mut vec, max, flags)` (or `accept_batch`), which keeps a multishot accept armed inside the listener: ≥ 1 connection per call, everything queued in one poll, re-created after an error, one task at a time (`ResourceBusy`), same `flags` on every call. For direct-only streams: `accept_batch_direct_into` (see Fixed files).
  - `TcpStream::recv_multi(&ring)` / `UnixStream::recv_multi` (6.0+) give a `RecvStream` of `SelectedBuf`s: EOF gives `None`; `Err(ENOBUFS)` from `next()` means the kernel ended the recv because the ring had no free buffer; dropping the stream returns queued buffers to the ring. Don't mix `recv_multi` with other reads on the same socket. `stream.next_rearm().await` (also `poll_next_rearm`; on `RecvStream` and `RecvBundleStream`) is `next` that never yields `ENOBUFS`: it waits for a free buffer without polling (each recycled buffer wakes one waiting stream, which has it to itself until its recv completes), re-arms and continues, no copy. It is still the slow path: while the ring is short, every chunk costs a re-arm (one SQE, one extra completion, about three task polls), so size the ring or give it a working set. `stream.rearm_on(&other)` continues on another ring of the same runtime: a recv that has ended is armed there at the next poll (with the same ring, a re-arm in place); one in flight is cancelled, the stream yields what the old ring still delivers, in order, then arms on the new one. `stream.ring()` is the ring in use. Mixing `next`, `next_rearm` and `read_into` is fine. For framed reads use `stream.read_into(&mut BytesMut)` (also on `RecvBundleStream`; feature `bytes`): copies all queued chunks, returns buffers at once, `Ok(0)` at EOF, re-arms after `ENOBUFS` itself (returns it only if the ring is still empty after a re-arm). `stream.into_reader()` gives a `MultiRecvReader` (`AsyncReadRent`, keeps one partly read buffer). Both cost one copy per byte.
  - Recv bundles (`IORING_RECVSEND_BUNDLE`, 6.10+): `TcpStream`/`UnixStream::recv_multi_bundle(&ring)` yields `Bundle`s, `recv_bundle(&ring)` receives once. A `Bundle` is an allocation-free iterator of `SelectedBuf`s in data order (`len()`, `bytes()`, `detach()`). With raw SQEs use `ring.take_bundle(cqe)` for bundle completions and `take` for the others; both mix on one ring in any order. Check `ring.supports_bundles()`; the wrappers return `Unsupported` without it. The kernel ends a multishot recv when the ring runs empty; `RecvStream`/`RecvBundleStream` re-arm themselves then (after `ENOBUFS` only through `next_rearm`/`rearm_on`; never after `cancel()` or EOF).
  - Size the CQ (`cq_size`) for multishot bursts.
- **Fixed files (5.19+).** `RuntimeBuilder::with_fixed_files(n)` registers a sparse file table of `n` slots the runtime hands out (off by default). `stream.register_fixed()?` (`TcpStream`, `TcpListener`, `UnixStream`, `File`) puts the fd into a free slot; every op after that (including zero-copy sends and `cancel_all`) names the slot (`IOSQE_FIXED_FILE`), saving the per-SQE file lookup and refcount. The fd stays open, so raw-fd APIs still work. `TcpListener::accept_direct()` / `accept_direct_with(flags)` accept straight into a slot and return a *direct-only* stream with no fd (`is_direct()`): `as_raw_fd()` is `-1`, `into_raw_fd` panics, `local_addr` and the sync option calls (`set_nodelay`, `nodelay`, `set_tcp_keepalive`) return `Unsupported` (options set on the listener are inherited), `peer_addr` comes from the accept, `shutdown` uses `IORING_OP_SHUTDOWN`. `accept_multi_direct(flags)` needs kernel-allocated slots from `with_fixed_files_kernel_alloc(k)` (6.0+) and yields a `DirectAcceptStream` without peer addresses. `OpenOptions::open_direct(path)` opens a regular file straight into a slot (`OPENAT` with `file_index`; a runtime slot, else a kernel-allocated one if `with_fixed_files_kernel_alloc` is set): a direct-only `File` (`is_direct()`, `as_raw_fd()` `-1`, `metadata()` `Unsupported` since `STATX` takes no fixed file); positional reads/writes, `read_fixed_at`, `fadvise`, `sync_*`, splice and `read_at_then_send` use the slot, and close is a slot removal, never an io-wq punt. A full table gives `ENFILE`. Slots are freed when the close completes; `uring::fixed_file_stats()` reports use. The table belongs to the runtime: don't `register_files`/`unregister_files` through `with_ring` on such a ring. `stream.fixed_slot()` gives the slot for hand-built `types::Fixed` SQEs. A slot belongs to its ring: keep the stream on that runtime.
  - **Direct-only sockets in a server.** `listener.accept_batch_direct_into(&mut vec, max, flags)` / `accept_batch_direct` is `accept_batch_into` on a multishot direct accept (needs `with_fixed_files_kernel_alloc`, `Unsupported` without; `TcpListener` only; streams have no peer address; armed separately from `accept_batch`). When all kernel slots are taken the accept ends with `ENFILE` **and the kernel closes the connection it had just accepted**: size the range for the peak and don't call again at once after `ENFILE`. What needs an fd elsewhere goes through a syscall or the ring, whichever the stream has: `stream.shutdown_with(Shutdown)` / `shutdown_both()` (`&self`, the future borrows nothing: call it from a supervisor task while the connection's task has ops in flight; receives end with `Ok(0)`, sends with `EPIPE`), `set_sockopt(level, name, &value)` (`value` passed byte for byte, use the C type), `unsafe get_sockopt::<T>(level, name)`, `set_nodelay_async(bool)`, `set_tcp_keepalive_async(time, interval, retries)`; `UnixStream` has the first four. The request is made by the call (syscall with an fd, SQE without), the future only carries the result, and dropping it does not cancel it: `IORING_OP_SHUTDOWN` is no longer cancelled when its future is dropped, on any stream. Ring socket options need Linux 6.7 (`Unsupported` before), `get_sockopt` through the ring reads only `SOL_SOCKET` options (kernel limit, still so on 7.0), and a ring shutdown always runs in an io-wq worker. Syscalls per connection from accept (with `TCP_NODELAY`) to close: 2 with an fd (`getpeername`, `setsockopt`), 3 with `register_fixed` (plus `io_uring_register`), 0 direct-only (`TCP_NODELAY` is one SQE, close a slot removal; a full shutdown adds one syscall with an fd, one SQE without); every op on a registered or direct-only stream skips the kernel's fd lookup and refcount. G1 (2000 connections): direct accept +0.4% against `register_fixed`.
- **Zero-copy sends.** `stream.write_zc(buf)` resolves after the kernel released the buffer. `stream.send_zc_early(buf).await` gives `(res, pending)` as soon as the send result is known; `pending.await` returns the buffer once the kernel released it (dropping `pending` is fine: the runtime keeps the buffer until then). `send_zc_fixed(buf)` / `send_zc_fixed_early(buf)` send a `FixedBuf`/`FrozenFixedBuf` with its `buf_index`; `send_vectored_zc(bufs)` uses `SENDMSG_ZC`; `send_auto(buf)` picks zero-copy from `monoio::net::ZC_MIN_LEN` (16 KiB, `zc_worthwhile`). Over loopback the kernel copies anyway. Stats (`metrics` feature): `zc_sends`, `zc_notifs`.
- **Cancel a whole connection.** `TcpStream::cancel_all()` / `UnixStream::cancel_all()` push one `IORING_ASYNC_CANCEL_FD | ALL` SQE (5.19+): every in-flight op on the socket, including those of split halves, resolves with `ECANCELED` (or its result) and gives its buffer back; keep awaiting them. Stat (`metrics` feature): `cancel_fd_pushed`.
- **Op slots.** Every in-flight op has a 64-byte slot (one cache line, 64-byte aligned, with and without `metrics`) in a paged table that grows without moving slots. **Dropped in-flight ops** keep their data in the slot until the kernel is done: inline (no allocation) up to 48 bytes and alignment 8, which covers recv/send/read/write with `Vec`/`Bytes`/`BytesMut`; larger data (e.g. the `Slice` of an owned buffer that `read_exact`/`write_all` use after a short op) is boxed. Stats (`metrics` feature): `ignored_inline`, `ignored_boxed`.
- **Linked chains.** `unsafe uring::submit_chain([sqe; N], data)` queues N SQEs as one unit: room for all is reserved first and nothing is submitted in between, so a link is never split. The caller sets the link flags (`IO_LINK` on all but the last, or `uring::link([..])`); a linking last SQE and `SKIP_SUCCESS` are rejected. It resolves to `([Cqe; N], data)` once all completed; links cancelled after a failure (or a short read, which breaks an `IO_LINK`) complete with `-ECANCELED`. Dropping it keeps `data` alive until the last CQE. Don't put `IO_LINK` on SQEs passed to plain `uring::submit`. Typed: `File::read_at_then_send(buf, pos, &tcp)` (a short read returns `UnexpectedEof` and nothing is sent).
- **Deadlines without the timer.** `TcpStream::read_with_deadline(buf, dur)` / `write_with_deadline` attach a kernel link timeout (`IORING_OP_LINK_TIMEOUT`): one extra SQE, no timer-wheel entry, works without `enable_timer`. On expiry they return `ErrorKind::TimedOut` with the buffer, and the stream stays usable. Raw: `unsafe uring::submit_with_timeout(sqe, data, dur)` (CQE `-ECANCELED` if it fired). `DriverStats::{chains_submitted, link_timeouts}` count them (`metrics` feature).
- **Request deadlines with the timer.** `time::timeout(d, fut)` makes a timer per call: a clock read, a wheel insert on the first poll (every op future is `Pending` on its first poll, so it always registers) and a removal on drop (a `Sleep` is 72 bytes at alignment 8). For a deadline around every request of a connection keep one `time::Deadline` per connection (56 bytes, `!Unpin`: `pin!` it, or `Box::pin` in a struct; panics without `enable_timer`): `let mut dl = pin!(Deadline::new());` then `dl.as_mut().timeout(d, serve_one(..)).await` arms, runs and disarms (`Err(Elapsed)` on expiry; pass `pin!(fut)` to avoid copying a large future). For several steps under one deadline: `dl.as_mut().arm(d)`, `with_deadline(dl.as_mut(), step).await?` per step (it neither arms nor disarms; after an `Err` it keeps failing until re-armed), `dl.as_mut().disarm()`. `arm` and `disarm` are single stores while the entry is in the wheel (the driver re-inserts it about once per deadline period); a disarmed deadline never fires and wakes nobody; `is_armed()`, `is_expired()`, `poll_expired(cx)` (ready while armed and expired); `arm_at(Instant)` is exact. G1, pipe path at 2000 connections, user instructions per frame: 1,798 with no deadline, 1,983 with a `Deadline` per connection, 2,433 with a `timeout` per frame (3,341 at G0); on the bench a `Deadline` matches a sweeper task that shuts stalled sockets (+0.2%). `time::timeout_coarse(d, fut)` is `timeout` without the clock read. `arm` and `timeout_coarse` use the coarse clock `time::Instant::recent()`: the latest clock read on this runtime thread, read at most once per round of tasks (after a park or a cold-path submit), never ahead of `now()`, never backwards, behind by less than one round; `now()` outside a runtime or without `enable_timer`. A coarse deadline can therefore come early by that lag and up to 2 ms late: use it for deadlines of seconds; `timeout()` keeps the exact clock. Behaviour that changed with this: the driver advances the wheel only when a timer is due, so a timer registered with a deadline that is already past (but after the wheel's time) fires in the next driver pass, before the runtime blocks, not inside the registering call; durations beyond about 30 years are capped instead of panicking; with no timer registered a park reads no clock; a timer entry keeps the waker of its latest poll, so a `Sleep` moved to another task wakes that task; a waker may create, reset or drop timers (no `RefCell` panic).
- **Cross-ring messages (`IORING_OP_MSG_RING`, 5.18+).** Hand out `uring::ring_handle()` (or `RingHandle::new(rt.driver())`; `Send + Sync + Clone`). It holds a dup of the ring fd, so it stays valid after the target runtime exits (messages then go nowhere or fail with `EOWNERDEAD`; drop handles of dead runtimes, their messages pile up in kernel memory). `uring::msg_ring(&h, id, res).await` posts a CQE `(id, res)` to the target's hook; it works with `single_issuer`/`defer_taskrun` targets and keeps one sender's messages in order. `msg_ring_nowait` just queues the SQE (`CQE_SKIP_SUCCESS`): no source completion, failures silently dropped. On the target, `uring::msg_receiver()` installs a hook feeding a `Mailbox` (`recv().await -> (id, res)`); if you need the hook yourself, create `Mailbox::new(lo..=hi)` and call `mailbox.offer(id, cqe)` from it.
- **Named op futures / token API.** `monoio::io::futures` has `Unpin + 'static` `RecvFuture`, `SendFuture`, `ReadvFuture`, `WritevFuture`, `ReadAtFuture`, `WriteAtFuture`, made by the `_op` methods: `TcpStream`/`UnixStream` (and owned halves) `recv_op`, `recv_with_flags_op`, `recv_poll_first_op`, `send_op`, `send_with_flags_op`, `readv_op`, `writev_op`; `File::read_at_op`, `write_at_op`. They take `&self`, push the SQE immediately and don't borrow the stream, so a struct can hold an in-flight op without `Box::pin` (steady state allocates nothing). In a hand-written state machine drive one with `fut.poll_result(cx)` (no `Pin`); `is_terminated()` says it already returned. Dropping one cancels it (with `async-cancel`) and the runtime keeps the buffer alive, but you lose the buffer: to get it back call `fut.cancel()` and keep polling (`ECANCELED` or the completed result). The trait `read`/`write`/`readv`/`writev` on socket streams return these futures.
- **File ops.** `file.fadvise(offset, len, monoio::fs::Advice::Random).await?` (`IORING_OP_FADVISE`, 5.6+; `len` 0 = to EOF, at most `u32::MAX`; `fadvise_raw` takes `libc::POSIX_FADV_*`). File/pipe splice (feature `splice`, 5.7+): `let (rx, tx) = monoio::net::unix::new_pipe()?;` then `file.splice_to_pipe(&tx, offset, len)` (explicit offset, 0 at EOF) and `rx.splice_to(&mut tcp, n)`; `file.splice_from_pipe(&rx, offset, len)` and `tx.splice_from(&mut tcp, n)` go the other way. File splices always run in io-wq workers (`REQ_F_FORCE_ASYNC`; `SPLICE_F_NONBLOCK` doesn't help): use them for large cold files; for cached files use `read_fixed_at` + `send_fixed` or `read_at_then_send`. Inline vs io-wq on Linux 7.0 (`tests/fs_punt_probe.rs`): inline: `openat` (cached path), warm 128 KiB `read` (fd or slot), `fadvise` NORMAL/SEQUENTIAL/RANDOM, direct open, close of a slot, close of an fd on ext4; io-wq: close of an fd on f2fs (filesystems with `->flush`), `splice`, `statx` (`metadata()`, `fs::read`), `fadvise` WILLNEED/DONTNEED; a cold read is neither (async buffered read, completes via task work). `Sequential` doubles the readahead window (re-advise after each open). `OpenOptions::custom_flags(libc::O_NOATIME)` skips atime updates (own files only, `EPERM` otherwise); `openat` runs inline only on a cached path lookup without `O_CREAT`/`O_TRUNC`, otherwise in an io-wq worker.
- **Submit errors.** IO methods don't panic when the SQ can't be flushed (e.g. EBUSY on CQ overflow): a full SQ is flushed and retried up to 8 times, then the op fails with EBUSY. Rent-style calls return `(Err(e), buf)` with the buffer.
- **Sharing the io-wq (`IORING_SETUP_ATTACH_WQ`).** `RuntimeBuilder::attach_wq(fd)` with `fd = primary.driver().as_raw_fd()` (works with `enable_timer()` too; call it after `uring_builder`). The primary runtime must outlive the others.
- **Thread-per-core helper** (`utils`). `utils::ThreadPerCore::new(cpus).run(|core| async move { .. })?` starts one OS thread per CPU; each pins itself, builds its runtime (default `RuntimeBuilder::new().enable_timer()`; `.builder(|core| RuntimeBuilder::<D>::..)` for any driver) and runs `block_on`. `run` returns only after every runtime is built; if one fails (pinning, build), no closure runs and it returns `Err`. `CoreInfo { index, cpu, cores, rings }`: `rings` has every core's `RingHandle` for `msg_ring` from the first poll. `.attach_wq(true)` shares core 0's io-wq; core 0's runtime is kept until the others end. `.thread_name(prefix)`. `TpcHandle::join()` gives `Vec<thread::Result<T>>` in core order. Per-core listeners: `TcpListener::bind_with_config(addr, &ListenerOpts::new().reuse_port(true))` on each core (the kernel spreads connections by hash). Example: `--example thread_per_core`.
- **Blocking work.** `monoio::spawn_blocking` needs `sync`. Attach a pool with `RuntimeBuilder::attach_thread_pool` or choose `with_blocking_strategy` (`Panic` or `ExecuteLocal`).

## Runtime configuration
Via builder or macro: `RuntimeBuilder::<IoUringDriver>::new().with_entries(n).enable_timer().build()`, or `#[monoio::main(entries = n, timer_enabled = true, worker_threads = n)]`.

- `entries`: io_uring ring size. Default 1024, minimum 256 (smaller values are raised to 256), 0 is a macro error. Larger rings mean fewer submits and more memory. The completion queue gets the kernel default of `2 * entries`; with multishot ops (many CQEs per SQE), raise it through `uring_builder(..)` with `setup_cqsize(n)` to avoid CQ overflow. The in-flight op table is not pre-sized: it grows in pages as ops are submitted.
- `enable_timer` / `timer_enabled`: off by default. `monoio::time::{sleep, interval, ...}` panics unless it is on. `std::time` is unaffected. `enable_all()` is also available.
- `worker_threads` (aliases `workers`, `threads`): default 1. With `n`, the macro starts `n-1` extra threads, each with its own runtime, plus the main thread. For pinned runtimes, one per CPU, use `utils::ThreadPerCore` (see Core concepts).
- `uring_builder(io_uring::Builder)`: tune the raw io_uring settings. Call it before the ring-flag methods below: it replaces the stored builder.
- Ring flags: `coop_taskrun()`, `taskrun_flag()` (needs `coop_taskrun` or `defer_taskrun`, EINVAL otherwise), `single_issuer()`, `defer_taskrun()` (also sets `single_issuer` and `taskrun_flag`, so completions are processed while tasks stay ready), `cq_size(n)`.
- `register_ring_fd()`: registers the ring fd (5.18+), saving an fd lookup per `io_uring_enter`. Falls back silently; check `driver().is_ring_fd_registered()`.
- `min_wait(wait, batch)`: a waiting enter waits for `batch` CQEs, or `wait` with at least one ready (6.12+, ignored otherwise). Adds up to `wait` of latency at low load. `uring::set_min_wait(wait: Option<Duration>, batch)` (or `IoUringDriver::set_min_wait`; with the timer `rt.driver().inner().set_min_wait(..)`) changes it at run time, from the next park on, e.g. to the number of replies in flight: two stores; `None` or `batch < 2` turns it off; `Unsupported` when a wait is asked for and the kernel lacks `IORING_FEAT_MIN_TIMEOUT` (the builder ignores it silently there). Kernel note: after an enter that asked for more than one completion (`min_wait`) `IORING_SQ_TASKRUN` can stay set with nothing pending, so with `min_wait` `enter_left_taskrun` over-counts (the share of waits that left work is not meaningful there), `skip_empty_enter` makes some enters it could have skipped, and `drain_taskrun` makes one empty enter per park: use `min_wait` or `drain_taskrun`, not both.
- `drain_taskrun(max)` (off by default; `0` is off; only on a ring with both `DEFER_TASKRUN` and `TASKRUN_FLAG`, which `defer_taskrun()` sets): after a waiting enter returned and its CQEs were reaped, enter again without waiting while the kernel flags task work (`IORING_SQ_TASKRUN`), at most `max` times, reaping after each, and only then run the ready tasks. Why: a `DEFER_TASKRUN` ring runs completions only inside `io_uring_enter`, and a wait returns as soon as it has one completion (an enter that slept delivers exactly one; one that did not sleep runs at most 20 task-work items, twice if it also submitted), so receives that become ready a moment after a bulk send's completion wait a whole round of tasks (G0: `defer` left task work behind after about 47% of its waiting enters, `coop` after 1–3%). One drain enter is one syscall, made only when the flag is set, never sleeps (no timeout, no `min_wait`), delivers at most 20 completions on Linux 6.13+ (everything pending on older kernels), and one that brings nothing ends the drain; it runs only after a park that waited, not on the cold-path submit. **Use `2` for request/response servers** (G1): with few connections next to bulk work `drain2` alone brings the replication rate within the 3% bound of `coop` without `min_wait` (with `send_eager` replies it is above `coop`, +1.9%), and at 2000 connections every drain enter comes back full, so each round only grows by `20 × max` frames, which costs throughput (G1: `drain2` −2%, at the bound; `drain4` −2.6% on the reproducer, not recommended). Stats (`metrics`): `drain_enters`, `enter_left_taskrun`.
- `skip_empty_enter()` (off by default): skip `io_uring_enter` between task rounds when nothing is queued. No effect on COOP/DEFER rings without `taskrun_flag`.
- `iowq_max_workers(bounded, unbounded)` (5.15+): caps `iou-wrk-*` threads (`0` keeps the current limit); `build()` fails if the kernel refuses. Rings sharing a wq via `attach_wq` share the cap, so set it on the primary.
- `sqpoll(idle, cpu)`: SQ poll thread (`IORING_SETUP_SQPOLL`, `cpu` = `SQ_AFF`), applied at `build()` (survives `uring_builder`). Give the poller its own CPU: on the loop's CPU it costs ~85% throughput. Without `cpu` it inherits the building thread's affinity, so `build()` warns once per process when that mask is one CPU and `cpu` is `None` or that CPU; `deny_sqpoll_conflict()` makes it fail with `InvalidInput`. SQPOLL set via `uring_builder` is not checked.
- `task_budget(n)`: run `n` ready tasks per round before checking the driver (default about 2× the queue length). A small `n` makes every waker hand-over (pool lease, channel) wait a whole queue traversal; combine it with `lifo_slot(true)`.
- `lifo_slot(true)` (off by default): a task woken by the running task runs right after it (one slot; a second such wake moves the earlier one to the back of the queue; at most 3 slot polls in a row; slot polls count against `task_budget`). CQE wakes, foreign wakes and self-wakes (`yield_now`) always use the queue.
- `small_io_priority(Some(n))` (off by default): a task woken by a completion whose result is below `n` (bytes, or an fd, 0, an error) goes to a priority queue that runs before the ready queue. A completion of ≥ `n` bytes marks its task as bulk: its next 8 small completion wakes still use the queue (covers the request read/open/close between a bulk task's chunks). At most half of a round's budget goes to the priority queue while other tasks are ready. Only useful with a small `task_budget`: then a request with k I/O steps waits ~k budget-sized rounds instead of k traversals of the whole queue. For small requests next to bulk streams: `task_budget(61)`, `lifo_slot(true)`, `small_io_priority(Some(16 * 1024))` (`n` above the request/response sizes, below the bulk chunk). Stat: `prio_polls`.
- `coop_budget(Some(n))` (off by default): per task poll, `n` ready results from op futures, `uring::MultiOp::next`, `submit_chain` and `task::consume_budget()`; then the next one wakes the task and returns `Pending` (the result stays queued). Op futures are `Pending` on their first poll, so this only limits tasks draining queued results. `AcceptStream`/`RecvStream` are not budgeted.
- Stats (needs the `metrics` feature; without it these APIs don't exist): `IoUringDriver::stats()` / `reset_stats()` (with the timer: `rt.driver().inner().stats()`), or `monoio::driver_stats()` inside the runtime. A `DriverStats` copy: enter calls (submit/wait/skipped), waiting enters after which `IORING_SQ_TASKRUN` was still set once their CQEs were reaped (`enter_left_taskrun`; only on rings with `taskrun_flag`, e.g. `defer_taskrun`; `enter_left_taskrun / enter_wait` is the share of waits that left work, not meaningful with `min_wait`), extra enters of `drain_taskrun` (`drain_enters`, also in the submit count; their CQEs count for the tick of the park in `op_ticks_by_opcode`), SQEs submitted, CQEs reaped, CQEs-per-tick histogram, SQ-full flushes, EBUSY retries, cancels pushed/lost, the kernel CQ overflow counter (read when you call `stats()`), ops by opcode, and per-opcode completion latency in driver ticks (`op_ticks_by_opcode`; under load a punted op lands in bucket 1+). io-wq punts are not visible directly; use the `io_uring:io_uring_queue_async_work` tracepoint.
- Scheduler stats (feature `metrics`): `monoio::runtime_stats()` / `reset_runtime_stats()` inside the runtime, or `Runtime::stats()` / `reset_stats()`. A `RuntimeStats` copy: rounds, cold-path submits, parks with `park_ns`/`busy_ns`, tasks polled and a polls-per-round histogram, `ops_completed` (CQEs of single-shot ops that woke a waiting waker: not multishot CQEs, not CQEs that arrive before the future's first poll, not dropped ops; `tasks_polled / ops_completed` is the task polls per op completion, below 1 when a task waits for several ops that complete in one tick), rounds cut by the budget, ready-queue length (last round) and high water, tasks spawned/completed, remote wakes, `coop_yields`, `lifo_polls`, `prio_polls`. Plain thread-local adds plus two `Instant::now()` per park; without `metrics` none of it is compiled.

**Recommended configuration for request/response servers** (G1, one configuration for few and many connections): `defer_taskrun()`, `skip_empty_enter()`, `register_ring_fd()`, `drain_taskrun(2)`; accept with `accept_batch_into` (or `accept_batch_direct_into` with `with_fixed_files_kernel_alloc`, else `register_fixed()` per stream); replies through `send_eager` and the next receive queued in the same task poll (`recv_poll_first_op`); receive buffers that keep their capacity (`clear()`, not `advance()`); for thousands of connections, multishot receive (`recv_multi` + `next_rearm`) on one `BufRing` with `working_set(16, 16)` and buffers that hold a whole frame (the first few dozen connections stay on per-connection buffers next to bulk work: all-multishot gives up 3% of frames and 30 µs of ack p99 there); request deadlines with one `Deadline` per connection. No `min_wait`. Measured against tokio on loopback (G1, 3 rounds): 2 encrypted 1 MiB streams + 9 replication connections: 55,173 frames/s, ack p99 204 µs (tokio 54,758, 230 µs); 2000 connections × 4 KiB: 113,212 frames/s, ack p99 18.6 ms (tokio 108,373, 18.8 ms); 8 connections × 4/16/64 KiB: 98,275 frames/s, ack p99 113 µs (tokio 92,557, 103 µs [103–120]). `coop_taskrun` is only right for a few connections next to bulk work, and only with batch accept; it is 13–18% slower at 2000 connections.

## TLS
Enable `tls-rustls` and/or `tls-native`. Both wrap any `AsyncReadRent + AsyncWriteRent` (usually `TcpStream`) and yield a stream implementing the rent traits, `Split` (so `into_split()` works) and `shutdown()` (sends close_notify). Handshakes return `Result<_, TlsError>`, which converts into `io::Error`. Tests: `monoio/tests/tls_*.rs`; runnable demos: the `tls-*` examples.

**rustls** (`monoio::tls::rustls`). Enable `tls-rustls-ring` (or `tls-rustls-aws-lc-rs`) for a crypto provider; the rustls crate is re-exported as `monoio::tls::rustls::rustls` (`ServerConfig`, `ClientConfig`, `RootCertStore`, `pki_types`, PEM parsing), so you need no `rustls` dependency. Pass rustls configs straight in:
```rust
use monoio::tls::rustls::{rustls::pki_types::ServerName, TlsAcceptor, TlsConnector};

// server: ServerConfig -> TlsAcceptor (From<ServerConfig> / From<Arc<ServerConfig>>)
let acceptor = TlsAcceptor::from(server_config);
let mut tls = acceptor.accept(tcp_stream).await?;            // ServerTlsStream<TcpStream>

// client: ClientConfig -> TlsConnector
let connector = TlsConnector::from(client_config);
let mut tls = connector.connect(ServerName::try_from("example.com")?, tcp_stream).await?;

let (res, buf) = tls.read(buf).await;                          // normal rent IO
let alpn = tls.alpn_protocol();                                // set via config.alpn_protocols
```
Types: `ClientTlsStream`/`ServerTlsStream` (+ `*ReadHalf`/`*WriteHalf`). There is no single unified stream type.

**native-tls** (`monoio::tls::native`). The crate is re-exported as `monoio::tls::native::native_tls` (`Identity`, `Certificate`, builders). Wrap the `native_tls` builders' output:
```rust
use monoio::tls::native::{TlsAcceptor, TlsConnector};

let acceptor = TlsAcceptor::from(native_tls::TlsAcceptor::new(identity)?);   // Identity::from_pkcs8(chain, key)
let mut tls = acceptor.accept(tcp_stream).await?;                            // TlsStream<TcpStream>

let connector = TlsConnector::from(native_tls::TlsConnector::builder()
    .add_root_certificate(ca).build()?)
    .read_buffer(Some(32 * 1024));                                           // optional; .write_buffer() too, default 64 KiB
let mut tls = connector.connect("example.com", tcp_stream).await?;
```
The client verifies the hostname against the domain you pass. `alpn_protocol()` needs `tls-native-alpn` (client side).

Notes: everything above is reachable through this crate alone (`monoio::io_uring`, `monoio::uring::libc`, `monoio::tls::{rustls::rustls, native::native_tls}`); `monoio/tests/reexports.rs` pins those paths. Both backends copy through a read and a write staging buffer (the sync engines need `std::io`), 64 KiB plus record overhead each by default; set them with `.read_buffer(Some(n))` / `.write_buffer(Some(n))` on either backend's `TlsAcceptor`/`TlsConnector` (values below 18 KiB, one full record, are raised to 18 KiB). Records are gathered and sent with one socket write per buffer, and `writev` feeds all slices to the engine before one flush. Opt-in write coalescing: `.write_coalescing(true)` on the acceptor/connector, or `stream.set_write_coalescing(true)` (before `into_split`): `write` only buffers, data goes out when the write buffer is full or on `flush()`/`shutdown()`, so you **must call `flush()`** before waiting for the peer (rustls also merges small writes into records of up to 16 KiB). Default off: data is on the socket when `write` returns. Do not drop a handshake or IO future midway: it takes the staging buffer, so the stream breaks (a later use may panic). Await it to completion. Interop between the two backends works (covered by `tests/tls_interop.rs`).

## Environment gotchas
- io_uring needs kernel 5.6+. Check at runtime with `monoio::utils::detect_uring()`. Containers and sandboxes often block io_uring syscalls.
- The memlock limit must be large enough (`ulimit -l`). 512 KiB is usually enough; use `unlimited` for high throughput or large `entries`. Set it in `/etc/security/limits.conf` (`* soft memlock unlimited`, `* hard memlock unlimited`; log in again) or systemd `LimitMEMLOCK`. Symptom of too little: IO fails with os error 105 (`No buffer space available`).
- On macOS or Windows, develop in a Linux VM, container, or WSL2.
- Tests and examples that use the timer need `enable_timer`; `#[monoio::test]` accepts the same attributes as `main`.
