# W2-m3: small-request p99 under bulk load (M3 retry)

Branch `r2/W2-m3` from `r2-g2`. New behaviour is opt-in (`RuntimeBuilder::small_io_priority`); a default
builder schedules exactly as before (`tests/lifo_slot.rs::default_is_fifo`,
`tests/small_io_priority.rs::default_keeps_completion_wakes_fifo`).

## Reproducer: `fairness --upstream`

The old `--hop` model (worker task + NOPs) has no real upstream I/O. `--upstream` models the SUT's proxy route:

- an upstream echo thread on its own CPU (`--upstream-cpu`, default the first client CPU, removed from the
  client set);
- a pool of `--pool` (64) upstream connections with the SUT's `common::pool` bookkeeping (idle reuse, lazy
  open, strict FIFO waiters, `put` wakes the front waiter);
- `--proxy-frac` (0.5) of the rr connections are proxy connections (request byte `p`): read request → lease →
  `write_all` `--rr-size` bytes upstream → `read_exact` them back → release → reply. The others answer
  directly (json). Both classes run at once, at `--rate` in total;
- server-side step times (window only, p50/p99): `lease`, `up_write`, `up_read`, `reply` (proxy) and
  `json_reply` (json: request read → reply written). JSON keys `json_p99_ms`, `proxy_p99_ms`,
  `step_<name>_p{50,99}_ms`; `runtime.prio_polls` with `metrics`.

M3 cell model (`64:4096`: ~410 stream connections, ~1,840 json and ~1,840 proxy connections at 1,000 req/s
each, 8 KiB echo):

```sh
fairness --bulk 400 --bulk-size 64k --chunk 64k --rr 3600 --rate 2000 --upstream --upstream-cpu 3 \
  --accept multi --warmup 3 --duration 8 [--budget 61 --lifo] [--small-io 16k]
```

Server on CPU 2, upstream on CPU 3, clients on the other 10 CPUs. `--features metrics` build.

## Mechanism

**One I/O step = one wait in the ready queue, and the proxy has twice as many steps as json.** Every CQE wake goes
to the back of the FIFO ready queue, which holds ~400–470 tasks under bulk load (the 400 stream tasks are always
ready: one 64 KiB send per poll). A task woken by a completion therefore waits for every queued task to be polled
once (a *traversal*), and an SQE it pushes is submitted only at the end of its round.

Server-side step times (r3 below, medians of 5 runs; `step` = from the end of the previous step):

| setting | rounds/s | `up_write` | `up_read` | `reply` | `json_reply` | json p50 | proxy p50 |
|---|---|---|---|---|---|---|---|
| default | 141 | 2.8 ms | 8.8 ms | 2.8 ms | 2.8 ms | 9.3 ms | 25.9 ms |
| `budget61:lifo` | 1,230 | 6.0 ms | 5.7 ms | 5.8 ms | 5.8 ms | 7.1 ms | 18.2 ms |

- json = request read (one wait) + reply (submitted at the end of the round): ~1–2 traversals.
- proxy = request read + upstream write + upstream read + reply: ~4 traversals, each a full wait. The upstream
  write is a small inline send, the upstream echo answers in microseconds, yet each costs a traversal. With the
  default budget `up_read` costs ~1.5 rounds: the reply from the other core arrives just after the enter that
  submitted the write, so its CQE is reaped one round later.
- `task_budget(61)` does not shorten a traversal (same tasks, same work, more enters), so every step costs the
  same full traversal (~6 ms here = ~470 tasks / 61 per round × ~0.8 ms per round). That is why json gets a bit
  better (fewer CQEs wait behind a long round) and proxy does not move: G2's "~40 ms in every setting".
- The pool is not the cause: the `lease` step is 0.00 ms at p99 (64 connections, ~20 in use). The LIFO slot only
  matters when it is contended (M2).
- tokio (1.54, `current_thread` + `LocalSet`, as in the SUT) is also FIFO for I/O wakes, with no LIFO slot; the
  LocalSet runs 61 tasks per tick, then the driver is polled (≈ `task_budget(61)`). Its proxy needs fewer waits
  because readiness I/O completes writes inside the poll: the upstream write and the reply cost no wake, so a proxy
  request is ~2 waits (client readable, upstream readable) vs monoio's 4. That matches the SUT ratios: tokio
  proxy/json p99 = 21.6/9.0 = 2.4, monoio 39/14 = 2.8–4.4.

So the fix has to make a small request's wake not wait for the bulk tasks: priority by kind of completion, plus
short rounds (so a priority task waits one short round, not the whole queue).

## Change: `RuntimeBuilder::small_io_priority(Option<u32>)`

- **Builder:** `small_io_priority(Some(n))`, default off (`Some(0)` = off). Context field `small_io_max`.
- **Driver (`driver/uring/mod.rs` `tick`):** with the option on, before completing a driver op it sets a
  thread-local hint from the CQE result: *small* (`res < n`, or an error) or *bulk* (`res ≥ n`), and clears it
  after. Off: one TLS read per tick, nothing per CQE.
- **Scheduler (`scheduler.rs`):** `push_woken` (a waker wake that is not the LIFO slot's) checks the hint when
  the option is on:
  - bulk completion → mark the task bulk (`Header::bulk = 8`, a `Cell<u8>` in the task header, 24 → 32 bytes),
    normal queue;
  - small completion → if the task is marked, decrement the mark and use the normal queue; otherwise push to a
    new priority queue;
  - no hint (task, timer, foreign, self wakes) → unchanged.
  The mark (8 small completions) covers a stream task's small steps between chunks (request read, open,
  close: ≤ 3 in the SUT's `stream_file`), so stream tasks never get the priority, while json/proxy tasks (8 KiB
  steps) always do.
- **Loop (`runtime.rs`):** order per pick is LIFO slot → priority queue (at most half of the round's budget,
  `prio_left`) → ready queue → priority queue (when nothing else is ready). `len()` counts the priority queue, so
  the runtime never parks with it non-empty.
- **Stats:** `RuntimeStats::prio_polls` (priority-queue polls within the round's share; `metrics` only).
- **Off path:** `prio_on` is a `Cell<bool>` checked in `push_woken`; `pop_next` checks `prio_left > 0` (0) and
  falls back to an empty `VecDeque` only when the queue is empty.
- **Tests:** `tests/small_io_priority.rs` (default stays FIFO; a small completion wake runs before the queue;
  a bulk completion marks the task for 8 small wakes, the 9th jumps the queue again, and a read below the
  threshold is a priority wake; `prio_polls` counted with `metrics`).

Why not alternatives:
- *Classify by completion size only* (first version): the stream task's request read is small, so with 64 KiB
  streams (one chunk per response) half of the stream wakes got the priority (18k prio polls/s instead of 6k)
  and json/proxy did not improve. The per-task bulk mark fixed that.
- *CQE wakes to the front of the queue*: every task is CQE-woken, so that only reverses the order.
- *Removing a wait in the proxy itself* (submit the upstream read together with the write, e.g. linked SQEs or
  `join!`) would save one step of four; a SUT change, independent of this one.

## Numbers

Machine **not quiet** (other agents compiling and benchmarking, load 2.5–4.5). Configurations interleaved per
round; medians with [min–max]. Server throughput is bimodal over time (~1,200 or ~2,500 MB/s, depending on
outside load on the server's SMT sibling); compare MB/s only within a round. The server core is saturated in
every run, so MB/s is the payload per server CPU-second.

**64 KiB cell model** (r3, 5 rounds; `--bulk 400 --bulk-size 64k --chunk 64k --rr 3600 --rate 2000 --upstream`):

| setting | json p50 | json p99 | proxy p50 | proxy p99 | MB/s | prio polls/s |
|---|---|---|---|---|---|---|
| default | 9.3 | 22.3 [12–24] | 25.9 | 43.5 [23–49] | 1,853 [1,206–2,558] | 0 |
| `budget61:lifo` | 7.1 | 18.7 [10–21] | 18.2 | 40.4 [22–45] | 2,260 [1,179–2,531] | 0 |
| `budget61` + `smallio16k` | 2.2 | 6.2 [3–7] | 5.6 | **10.9 [5–12]** | 1,195 [1,170–2,597] | 6,000 |
| `budget61:lifo` + `smallio16k` | 1.9 | 6.6 [3–7] | 5.1 | **11.1 [6–13]** | 1,491 [1,184–2,559] | 6,000 |

In the quiet rounds (3 and 4, ~2,500 MB/s for all): proxy p99 default 24.3/45.6, `budget61:lifo` 21.8/40.4,
`+smallio16k` **5.4–5.8 ms**, json p99 2.7–3.2 ms (default 12.4–23.3); MB/s 2,502–2,597 vs default 2,524 (tie).
In every round each `smallio` row beats both other rows on json and proxy p99, with MB/s within the round's
noise. Proxy p99/json p99 drops from ~2 to ~1.7; steps take ~1.2 ms (one 61-task round) instead of 3–9 ms.

More settings (64 KiB, 3 rounds, `m3-64k`):

| setting | json p99 | proxy p99 | MB/s |
|---|---|---|---|
| `smallio16k` without a task budget | 20.7 | 43.5 | 1,248 |
| `budget16:lifo` + `smallio16k` | 5.2 | 6.7 | 1,219 [1,206–2,437] |
| `budget61:lifo` + `smallio16k` | 6.2 | 10.4 | 1,261 |

Without a budget a round is the whole queue, so the priority changes nothing (as documented). Budget 16 is a bit
faster again in latency; 61 is the tokio-equivalent and was cheaper in G2 (`budget16:lifo` payload −7.8%).

**1 MiB streams** (`--bulk-size 1m --chunk 128k`, M1-like, 3 rounds, `m3-1m`):

| setting | json p99 | proxy p99 | MB/s |
|---|---|---|---|
| default | 60.9 | 121.9 | 1,774 |
| `budget61:lifo` | 37.4 | 101.4 | 1,740 |
| `budget61:lifo` + `smallio16k` | 6.8 | **13.2** | 1,717 (−1.4% vs `budget61:lifo`, tie) |

**M2 model** (`--bulk 400 --rr 200 --rate 2000 --hop`, 1 MiB/128 KiB, pool hand-overs through wakers, 3
rounds, `m3-hop`): `budget16:lifo` rr p99 35.3 ms → with `smallio16k` 5.6 ms (`budget61:lifo:smallio16k` 6.7 ms),
100% achieved, MB/s 1,783 / 1,743 / 1,775 (ties). The lease hand-over still goes through the LIFO slot; the
priority queue only takes the CQE wakes.

## What to bench

SUT tune item (new; e.g. `smallio<N>` with N in bytes, or `smallio` = 16384):

```rust
rb = rb.task_budget(61).lifo_slot(true).small_io_priority(Some(16 * 1024));
```

i.e. `--tune budget61:lifo:smallio16k`. Variants on `--cells 64:4096`, 5 rounds: `tokio`, `monoio`,
`monoio:budget61:lifo`, `monoio:budget61:lifo:smallio16k`, optionally `monoio:budget16:lifo:smallio16k`; plus
`--cells 1024:4096` with `acceptbatch:budget61:lifo:smallio16k` (M1 must stay at 0 timeouts). 16 KiB sits above
the SUT's small sizes (json body, 8 KiB echo request/upstream/reply) and below its stream chunk (64 KiB file
reads and sends). Expect proxy p99 well under 20 ms if the SUT behaves like the model; the risk is payload/CPU-s
(the reproducer saw a tie, but its noise floor is a few %).

Caveats: if a request read in the SUT ever returns ≥ 16 KiB (pipelining, large bodies), that task is treated as
bulk for its next 8 wakes. The repl workload's frames (4–64 KiB) are classed by their size.
