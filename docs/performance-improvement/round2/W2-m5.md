# W2-m5: many connections, small frames (M5)

Branch `r2/W2-m5` from `r2-g2`. Files: `driver/uring/{mod,lifecycle}.rs`, `utils/slab.rs`,
`scheduler.rs`, `task/mod.rs`, `runtime.rs`, new example `monoio/examples/smallframes.rs`
(`[[example]]` in `monoio/Cargo.toml`). No API change, no behaviour change, nothing to opt in.

## Short answer

- The gap is in the kernel, not in the runtime. On the local reproducer the server spends about
  36,000 cycles per 4 KiB frame. About 2,600 of them are user space (7%), all of monoio plus the app.
  Even a free runtime would not close an 8% gap.
- The code changes cut user instructions per frame by 5% (2,925 → 2,770) and are neutral to +1% on
  frames per CPU-second. That is inside the noise of this machine.
- Fixed files remove `fget`/`fput` (about 1.4% of server cycles here, about 2% in the lead's
  profile) but were neutral on frames per CPU-second locally. Still worth one bench run.

## Reproducer: `smallframes`

```sh
cargo build --release -p adaptif-gatotkaca-monoio --example smallframes
target/release/examples/smallframes --conns 2000 --size 4096 --duration 4   # --size 16k, --fixed, --depth, --ring ...
```

- Server: one runtime pinned to `--cpu` (2), `with_entries(4096)`, timer on, `accept_batch_into`.
  Per connection: read into a `BytesMut` (`slice_mut`) until a whole frame is there, then
  `write_all` of a 16-byte ack. Each frame runs under `monoio::time::timeout(10 s)`, like the bench.
- Clients: monoio runtimes on `--client-cpus` (4,6). Closed loop with `--depth 2` frames in flight
  per connection, so the next frame is usually queued when the server issues its recv (like the
  overloaded open loop of the bench: no poll arming).
- Output: frames/s, frames per CPU-second of the server thread (`getrusage(RUSAGE_THREAD)`), and
  per frame: user cycles, user instructions, all cycles (`perf_event_open` on the server thread,
  works with `perf_event_paranoid` 1). User instructions per frame are exact and noise-free, which
  makes small runtime changes visible.
- It lands at about 118k frames per CPU-second (4 KiB) and 90k (16 KiB), close to the bench cell.

## What the profiles say

Lead's profile (`m5-monoio.data` vs `m5-tokio.data`), symbols only monoio pays, in % of cycles:
`slab::Ref::remove` 1.43, `io_free_batch_list` 1.43, `__io_submit_flush_completions` 1.40,
`io_sendmsg_prep` 1.20, `io_recvmsg_prep` 1.15, `fget` 0.84, scheduler/task/op code about 3,
other io_uring issue path (`io_issue_sqe`, `io_send`, `io_recv`, `io_submit_sqe`, `io_init_req`, ...)
about 2.5. Tokio pays instead `entry_SYSCALL_64` 1.57, libc `recv` 1.24, `sock_recvmsg` 1.15,
`__sys_sendto`/`__sys_recvfrom` about 1, and the epoll callbacks. Net, io_uring's per-request
kernel work costs a few % more than two plain syscalls per frame on this load. That is the bulk of
the gap.

Why `remove` looked expensive: `Entry<MaybeFdLifecycle>` is 72 bytes (`Lifecycle` 64, of which the
inline `IgnoredData` is 56, plus `is_fd`/`kind`). With a 72-byte stride most slots straddle two cache
lines. `remove` moved the whole entry out (memcpy of 64+ bytes) and `poll_op` then matched on the
copy; the samples sit on the stores right after loading the second line. It is a cache miss on a
slot that went cold over a round with 2,000+ ops, not slow code. In the local profile
`complete` (in `tick`) took the first miss of the slot (2.5% of user cycles); after the fast path the
same misses showed up in the next things touched (`wake_by_val` on the task header, the timer
entry). The user side is latency bound: about 2,600 cycles for 2,900 instructions per frame.

Ring settings tried on the reproducer (5 interleaved runs each, medians): entries 4096 / 1024 / 512,
`setup_no_sqarray`, `coop_taskrun + taskrun_flag`, `register_ring_fd`. All within ±2% (noise).

## Changes

1. `Ref::complete` fast path (`lifecycle.rs`). The last CQE of a single-shot op whose future waits
   (`Waiting`) or was not polled (`Submitted`) writes `Completed` in place and wakes. Before, every
   CQE did `mem::replace` of the 64-byte state, a big match, a drop-glue call and a 64-byte write
   back. Everything else (multishot, `F_MORE`, zero-copy, dropped ops) goes to the unchanged
   `complete_slow`.
2. `Ref::poll_op` takes the result out of the `Completed` slot in place and frees the slot with the
   new `Ref::remove_forget` (marks it vacant, no move of the entry, no drop). `Slab::remove` reads the
   entry with `ptr::read` instead of `mem::replace`; the rare page compaction is a cold function.
3. `tick` copies CQEs out of the ring in batches of 32 (`CompletionQueue::fill`) and prefetches the
   op slot 4 CQEs ahead and the task header of the waiting waker 2 CQEs ahead. Only the CQEs present
   when `tick` starts are handled, as before. The CQ head is now published per batch instead of at
   the end (the kernel can reuse entries sooner; nothing reads them again).
4. The run loop prefetches the header of the next queued task before polling the current one
   (`TaskQueue::prefetch_next`).

Prefetches are hints (`_mm_prefetch`, x86_64 only, no-op elsewhere). They never fault and never
change behaviour.

## Numbers (local reproducer, 4 KiB, 2000 connections; noisy shared machine, interleaved runs)

Run 1, 10 rounds each, medians:

| build | frames/CPU-s | cycles/frame | user cycles/frame | user instr/frame |
|---|---|---|---|---|
| base (`r2-g2`) | 118,864 | 35,945 | 2,575 | 2,924 |
| + 1, 2 (fast paths) | 119,338 | 35,852 | 2,734 | 2,637 |
| + 3 (CQE batch, slot prefetch) | 119,340 | 35,822 | 2,606 | 2,698 |
| + 4 (task prefetch in run loop) | 119,602 | 35,770 | 2,600 | 2,725 |
| + waker/task prefetch in `tick` (final) | 120,140 | 35,564 | 2,550 | 2,770 |

Run 2, 6 rounds: base 118,936 vs final 118,618 (4 KiB); base 91,952 vs final 92,154 (16 KiB).
Run 3, 8 rounds, final build: 4 KiB 117,557, with `--fixed` 117,580; 16 KiB 89,016, with `--fixed`
87,246.

Reading: the changes save about 150 instructions per frame and are neutral within ±1% on
throughput. They are kept because they are safe and cut work on every op; do not expect them to move
M5 by much. Fixed files remove `fget` (0.23%), `fput` and part of `io_free_batch_list` (0.50 → 0.25%)
of the profile but did not change frames per CPU-second here.

## What the lead should measure

1. The M5 cell (4 KiB and 16 KiB, `--tune acceptbatch`) on this branch vs `r2-g2`: expect 0 to +1%.
2. The same cell with `--tune acceptbatch,fixedfd`: `fget` + `fput` were about 2% of cycles in your
   profile (`fget` 0.84%, `io_free_batch_list`→`fput` 1.13%). Fixed files remove them. That is the
   largest single item left that monoio can remove; expect 0 to +2%.
3. If both together stay outside 8%: the rest is io_uring's per-request kernel path (prep, issue,
   CQE posting, request free) against two plain syscalls. Options that change the model, not the
   runtime: multishot recv with a provided-buffer ring (already measured neutral), or bundles
   (`recv_multi_bundle`, 6.10+) to cut recv requests per frame. Worth one run each with the
   `smallframes` reproducer first.
