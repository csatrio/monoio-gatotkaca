## M1: confirmed, accept starvation (hypothesis 1)

`results/r2/g0-m1-diag` (metrics build, 1 round, `--cells 1024:4096`, monoio): 6,520 json / 6,535 proxy timeouts,
the same as run 87.

Per second during the measured window (`sut.stderr`):

| | value |
|---|---|
| accepts/s | 95–106, **exactly one per round** (`accepts == rounds == submits`) |
| tasks polled per round | ~430 (polls-per-round bucket 256–511) |
| round length | ~10 ms (≈ 100 rounds/s) |
| ready queue | 415–490 |
| `enter_wait` / parks | 0: the loop never parks, every round ends with a cold-path `submit()` |

Listener accept queue (`ss -lnt` Recv-Q of the SUT port, sampled each second): climbs to **3,338** during the
connection ramp, then drains at ~100/s (3,231 → 1,117 over 21 s). `TcpExtListenOverflows`/`ListenDrops` stay 0:
nothing is dropped, connections wait accepted-by-kernel but not by the server, and their 10 s timer runs.

`results/r2/g0-m1-acceptmulti` (perf build, 3 rounds, `--discard-first`):

| variant | timeouts json / proxy per round | json % / proxy % of target | json p99 | proxy p99 | stream MB/s | stream p99 |
|---|---|---|---|---|---|---|
| tokio | 0 / 0 | 95.0 / 95.0 | 12.6 ms | 31.6 ms | 1,593 | 716 ms |
| monoio | 6,221–6,334 / 6,237–6,349 | 69–70 / 68–69 | 21.6 s | 21.5 s | 2,323 | 206 ms |
| monoio `acceptmulti` | **0 / 0** | 94.9 / 94.4–94.6 | 26.9 ms | 132 ms | 2,269 (−2.3%, tie) | 211 ms |

**Conclusion.** M1 is the accept loop: one accept SQE in flight, so one accept per round. Multishot accept removes all
timeouts with no throughput cost. What is left on this cell is M3 (proxy p99 132 ms vs tokio's 32 ms; json p99 27 vs
13 ms), i.e. steady-state fairness, not starvation. The reproducer shows the same (W0-repro notes): `--accept single`
~60 accepts/s, `multi` ~400/s.

Consequences for wave 1:
- **W1-net:** the fix is runtime-side ergonomics plus documentation. Make "accept everything that is queued per poll"
  the obvious API (`accept_batch` or documenting `accept_multi` as the server accept loop). The benchmark server
  switches its default accept loop to multishot. That is a SUT change, applied to both SUTs' accept semantics: tokio
  already drains the queue per wakeup.
- **W1-sched:** coop must not throttle the accept loop's drain of queued multishot CQEs (`unconstrained`, or exempt
  multishot `next()` from the budget by default; decide and document).

## M2: confirmed mechanism, intra-round wakes wait a full traversal

Reproducer (metrics build, `--bulk 400 --rr 200 --rate 2000 --duration 8`):

| flags | rr p50 / p99 | achieved | rounds/s | queue |
|---|---|---|---|---|
| default | 19.7 / 27.9 ms | 100% | 78 | 456 |
| `--budget 16` | 14.7 / 19.2 ms | 100% | 2,194 | 453 |
| `--hop` | 19.7 / 27.9 ms | 100% | 78 | 455 |
| `--hop --budget 16` | **565 / 1,163 ms** | 91.8%, 200 unfinished | 2,547 | 528 |
| `--hop --budget 61` | 41 / 332 ms | 100% | 655 | 488 |
| `--hop --budget 256` | 30 / 35 ms | 100% | 155 | 482 |

SUT (`results/r2/g0-m2-diag`, metrics build, 1 round, `--cells 64:4096`): default proxy p99 41 ms; `budget16` json
p99 10.0 ms (better) and **proxy p99 18.0 s**, with ~7,400 rounds/s × 16 tasks and a queue of ~423.

**Mechanism.** With the default budget (2 × queue length), a task woken by another *running* task (a waker hand-over:
pool lease, worker, reply) is pushed to the back of the queue but still runs later in the **same round**. With a fixed
`n` far below the queue length, the same wake waits for a full traversal of the queue: ~500 / 16 ≈ 31 rounds, each
with its own `io_uring_enter`, ≈ 12 ms per hand-over. The lease is held across ~3 hand-overs, so the pool of 64 leases
serves ≈ 64 / 36 ms ≈ 1,800 req/s, below the offered rate, and the waiter queue grows without bound (p50 → seconds).
json has no hand-over, so it only sees the benefit (more frequent reaping). CQE-driven wakes are unaffected: they
wait one traversal under every budget.

Consequences for wave 1 (W1-sched):
- The LIFO slot targets exactly this: the woken task runs right after the waker. Expect `budget16 + lifo` to keep
  json's gain and fix proxy.
- An alternative that keeps budget semantics: tasks woken *by a task during the round* are not charged to `n` (the
  default budget already behaves like that implicitly). Try both in the reproducer; LIFO is the tokio-compatible one.
- "Reap without enter" is secondary: enters/round are not the cause, the traversal length is.

## Other observations

- **`park_ns` is not idle time.** In the reproducer's default run, `park_ms` ≈ 992 ms/s while CPU is at 100%: the
  `io_uring_enter(wait)` call does the inline socket sends of the submitted SQEs (128 KiB copies) before waiting.
  `park_ns` is "time inside the waiting enter", which includes kernel submission work. Document it that way in
  `RuntimeStats` (W1-sched owns `runtime.rs`); a true idle measure would need the time from the enter's return of
  the first CQE, which the kernel doesn't report.
- **Default accept is slow on the 64 KiB cell too:** ~290 accepts/s (one per round) still at t = 12 s in
  `g0-m2-diag`. No timeouts there because rounds are shorter, but the ramp is ~25 s long.

## M4: same cause as M1 (screening, 1 round)

`results/r2/g0-m4` (perf build, `--cells 64:4096`, 10 s):

| variant | timeouts json / proxy | json p99 | proxy p99 | payload MB/CPU-s |
|---|---|---|---|---|
| `fixedbuf` | 122 / 124 | 10.6 s | 10.6 s | 1,376 |
| `zc` | 133 / 134 | 10.6 s | 10.7 s | 1,369 |
| `fixedbuf` + `acceptmulti` | **0 / 0** | 16.2 ms | 44.7 ms | 1,355 |
| `zc` + `acceptmulti` | **0 / 0** | 15.4 ms | 50.5 ms | 1,396 |

Both variants are ~12% slower per CPU-second than the default (1,564), so rounds are longer, the one-accept-per-round
ramp lasts longer, and the tail of the ramp crosses 10 s. There is no registration or notification stall. **M4 needs
no runtime fix**; package W1-bufzc is dropped. G2 confirms with 3 rounds.

## Baseline: 0.7.1 vs the fork without `metrics` (G1, first half)

Interleaved A/B, 5 rounds, order alternating per round, 1-round runner invocations (`r2-bins/ab.sh`), no discard
run (each run has its 5 s warm-up). `results/r2/g1-base-64k`, `results/r2/g1-base-enc`.

|---|---|---|---|---|

| | json p99 / proxy p99 | 13.9 / 44.4 ms | 14.9 / 43.1 ms | +7.1% / −3.0%, ties |
| encrypted 1 MiB × 2 + repl 8 | payload MB/CPU-s | 1,525.6 | 1,541.3 | +1.0%, tie |
| | repl fr/s / repl p99 | 27,597 / 0.553 ms | 27,739 / 0.521 ms | +0.5% / −5.8%, ties |

**Passes:** without `metrics` the fork is no worse than 0.7.1. The per-op counters were cheap, so removing them shows
no measurable gain at this resolution either. That is expected: the point of the gate is that compiling metrics out
costs nothing and that turning metrics into a feature didn't regress anything.
